## Run locally

Requires Node.js 22.12 or newer, .NET 8, and the existing server's configured SQL Server connection.

Start the updated API from the `ParallelSystems.Server` directory:

```powershell
dotnet run --project ParallelSystems.Api.csproj --launch-profile http
```

The server's normal database initializer installs the task table scripts `021`–`040` and the task, notification, comment, attachment, checklist, label, dependency and board presentation procedures on startup. Use an appropriate development database when developing.

In this frontend directory:

```powershell
npm ci
npm run dev
```

Open `http://127.0.0.1:5174/task-management/`. Vite forwards only `/api/task-management` to `http://localhost:5185`. Set `PARALLEL_SYSTEMS_API_PROXY` before starting Vite if the API uses another address. Port 5174 is strict so another app does not silently receive the wrong port.

Enter your username or Staff Information email first. An existing account opens the password step. A unique staff email without an account opens Create account; choose a username and matching passwords (minimum eight characters). The server creates an active standard `User` account linked to that staff record, then the screen asks you to sign in. Task Management has its own login session; Timesheet/Receipts cookies cannot sign you into this app. No sample tasks/accounts are seeded in application databases.

Files save separately from task details and add History entries without changing the task version. Queued files stay in component memory and participate in navigation/sign-out protection.

## Hosting

Build with `npm run build` and serve `dist/` at `/task-management/`. Configure the web server to return `/task-management/index.html` for frontend routes such as `/task-management/tasks`. Proxy `/api/task-management/` to the updated API without rewriting its path. Use HTTPS in production. The API's existing forwarded-header configuration must trust the reverse proxy so secure cookies are issued on HTTPS requests.

The cookie `ParallelSystems.TaskManagement` uses the dedicated `TaskManagement` authentication scheme and is scoped to `/api/task-management`. Login, session check, and logout are under `/api/task-management/auth`. The cookie is HttpOnly and SameSite=Strict; each mutation sends `X-Task-Management: 1`. The app's session lasts 8 hours, or 24 hours with Remember Me, with sliding renewal. Existing shared authentication remains separate.

## Explicit Task Management reset

The SQL procedure is created by updated Server initialization. It is never called automatically and has no HTTP endpoint. Stop the application/API and connected task clients before running it manually in the intended database as db_owner or sysadmin:

```sql
EXEC app.sp_WorkTaskManagementReset @Confirmation = N'RESET TASK MANAGEMENT';
```

The explicit reset removes all tasks, task activity/history, comments/mentions, attachments and cleanup metadata, checklists, labels/assignments/audit, dependencies/audit, notifications, old discipline workflow publications/drafts/history, catalog customizations and board/status configuration history. It restores four shared default statuses for both disciplines, empty workflow activations and the four default board columns. Status/board revisions advance to reject pre-reset browser snapshots; task numbering restarts at one. Shared users, Staff Information, projects, Timesheets (including work_sessions and daily_work_sessions), receipts and other application data are preserved by an explicit table allowlist. Restart/reload the application afterward.

The procedure requires the exact confirmation phrase and database-owner/system-administrator privileges, refuses an ambient transaction, and wraps deletion plus seeding in one transaction. A failure rolls back all changes. It returns a summary and a second result set listing exact storage provider/bucket/region/key values for external attachment cleanup. It does not delete physical local/S3 files; save that manifest and clean only those objects separately using the configured storage administration tools.

No reset was run against the application database during implementation. Reset checks run only in the disposable test database.
