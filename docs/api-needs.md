# Task Management API extensions

## Notification inbox — current contract (2026-10-20)

- GET `/notifications?filter=all|unread&page=1` returns `{items,unreadCount,totalCount,page,pageSize}`. The fixed page size is 25. Items are unread first, newest ID first within each group; counts include only the caller's notifications for currently accessible tasks. `unreadCount` covers all pages independently of the filter; `totalCount` matches the selected filter. Omitted queries default to All/page 1. Nonpositive pages or unknown filters return 400; pages past the end clamp to the last page, or page 1 for an empty inbox. No-store responses.
- POST `/notifications/read-all` marks every currently accessible unread notification for the caller as read, across all pages, and returns 204. Idempotent; read history, other recipients and inaccessible task notifications are preserved. Existing POST `/notifications/{id}/read` remains scoped and available.
- The Notifications page stores filter/page in its URL, shows exact unread and filtered totals, and uses Previous/Next. Desktop/mobile badges cap at `99+`. Read mutations refresh the selected page; Mark all resets to page 1. Request identity guards prevent pre-mutation refreshes and expired-session replies from restoring old counts. No native desktop notifier or general notification endpoints change. Deploy updated Server before frontend.

## Project custom fields — current contract (2026-10-19)

- GET `/projects/{projectId}/custom-fields` returns `{version,projectId,canManage,fields:[{id,name,type,isArchived}]}` using the global task-column revision. Members see active definitions; administrators also see archived definitions. Existing project visibility and administrator mutation permissions apply.
- POST that path creates `{version,name,type}`; PUT `/{fieldId}` renames with the same body and unchanged type. POST `/{fieldId}/archive` or `/restore` sends `{version}`. Mutations return the complete definitions page. A project can have 30 total definitions. Trimmed names are 1–80 characters and unique ignoring case, including archived fields; built-in labels are reserved. Types are exactly Text, Number, Date, Checkbox and Person and cannot be changed after creation.
- Task-column layout responses add active `customFields`. Project layouts accept `custom:<lowercase-field-guid>` belonging to that project; default layouts cannot contain custom fields. Inherited layouts append active definitions. Creation/restoration appends to saved overrides, archive removes from them, and any definition mutation advances the global layout revision. Required built-in columns remain enforced; maximum layout size is 38.
- Task records include `customFieldValues:[{fieldId,value}]` with string/null values for active fields in their current project. Live task creation/update accepts optional `customFieldVersion` plus a **sparse patch** `customFieldValues`. Each submitted ID must be unique, active and in the target project. Explicit null/empty string clears that field; omitted IDs preserve existing values. Omitted, null or empty-array payloads preserve all values. The frontend omits the entire payload/version when no custom fields were edited, and sends only edited IDs, protecting unseen values from prior projects or restored fields. Archived/former-project values remain stored but hidden.
- Values are Text up to 2000 characters, invariant decimal Number within decimal(28,8) without exponent notation/rounding, strict YYYY-MM-DD Date, Checkbox strings `true`/`false`, or Person staff GUID. Number strings retain precision in the browser. Ordinary/bulk taskInput payloads omit these fields. Custom Person values do not change task ownership, participants, access or notifications. Task revision and global configuration revision protect atomic saves; stale definitions require reload.

## Task columns — current contract (2026-10-19)

- Authenticated GET `/task-columns/{discipline}` reads shared defaults; GET `/task-columns/projects/{projectId}/{discipline}` reads the effective profile for a visible web project. Discipline is exactly `Development` or `Drafting`. Responses are `{version,projectId,discipline,usesDefault,canManage,columns}` with an ordered array of field IDs and a global monotonic configuration revision.
- Administrator PUT on either path sends `{version,columns}`. Project POST `.../{discipline}/use-default` sends `{version}` and resumes live default inheritance. All writes use the existing dedicated cookie, no-store transport and protected request header. Any scope write increments the global revision; unrelated settings changes may therefore return 409 and require reload.
- Built-in fields are `task`, `discipline`, `status`, `priority`, `originalAssignee`, `assignedTo`, `qa`, `dueDate`; active project custom IDs are also supported as described above. Unknown/duplicate fields and omission of any required field (`task`, `discipline`, `status`, `priority`, `assignedTo`, `dueDate`) are invalid. Required fields may be reordered; built-in `originalAssignee`/`qa` and custom fields are optional. Development initially shows all built-ins in that order; Drafting initially omits `qa`. The display label for `assignedTo` is exactly Assigned To and resolves the current owner.
- Visibility/order settings affect list columns and board-card information only. They never mutate task values, assignment/workflow, labels/checklists or permissions. Custom definitions and task-value editing are separate operations. Cross-project filters do not select a project profile. The frontend guards request identities and revision floors, invalidates all scopes on newer revisions, and clears inaccessible project/session caches. Existing task and board-layout APIs stay separate.

Fresh catalog and explicit reset (2026-10-15): new/reset Task Management databases seed only To Do, In Progress, In Review and Completed for both disciplines. Migration 047_work_status_defaults stores these definitions separately and enforces normalized catalog-name uniqueness when existing names are clean; reset installs that index after clearing old duplicates. Old workflow stage names/task statuses are no longer imported by migration 045. Normal startup preserves saved definitions and does not wipe data. GET /statuses and /board-presentation include server-derived isCustom; StatusCatalogTable displays Default or Custom. Added/renamed names must be unique regardless of case or surrounding spaces in the UI, protected API writer and database index. Classification ignores client-supplied isCustom. Existing dirty development databases can start for explicit reset; they are not automatically consolidated or migrated. Evidence: those migrations, WorkStatusDefinition, WorkStatusesController, sp_WorkStatusesGet/Save, sp_WorkCatalogBoardGet, statusCatalog.js, liveStatuses.js, StatusCatalogTable.jsx and TaskManagementResetChecks.cs.


Comments, mentions and file attachments were implemented on 2026-10-13; task checklist items, labels, informational dependencies and board presentation were implemented on 2026-10-14 in the frontend and sibling Server. Discipline workflows were added on 2026-10-15. Sections explicitly marked as proposals remain unimplemented. All paths below use `/api/task-management`, the dedicated cookie, no-store responses, and `X-Task-Management: 1` on mutations.

## Linked tickets — current UI contract (2026-10-19)

- The task detail UI replaces Dependencies with Linked tickets: one optional parent, multiple children, cross-project links and independent status/owner. Legacy dependency records/endpoints remain separate and are not automatically migrated.
- `GET /tasks/{taskId}/links` returns `{version,canManage,parents:[{taskId,code,title,status,statusName,projectId,version}],children:[same],changedTasks:[]}`. Reads filter each endpoint through existing visibility. Members see only their visible relationships; links do not grant access.
- Administrator `POST` and `DELETE /tasks/{taskId}/links` use `{childTaskId,parentTaskId,version,childVersion}`; the context task must be an endpoint. `version` is the context ticket revision; `childVersion` is the child revision. DELETE removes exactly that pair. Successful writes return the page and `changedTasks:[{id,version,updatedAtUtc}]` for both endpoints. Standard 409 conflicts, 400 invalid/self/cyclic/already-parent relationships, and 404 unavailable endpoints apply.
- `POST /tasks/live` accepts optional nullable `parentTaskId` and creates the task and relationship atomically. An unavailable supplied parent is rejected rather than ignored. Existing detail updates do not send this field; relationship changes use the link editor. No blocking status rule or automatic owner/status change is introduced.
- Frontend evidence: `TaskLinkedTickets.jsx`, `linkedTicketState.js`, `TaskPage.jsx`, `taskNavigation.js`, and `tests/linked-ticket*.test.js`. Linked-ticket writes participate in navigation/draft guards and invalidate endpoint caches. Creating a child inherits an available web project context. Historical task project IDs absent from project lookups fall back to ordinary task routes; child creation keeps the parent and allows project selection. General tasks retain their General routes. Temporary parent query parameters are removed on save/cancel/ordinary creation.

## Common contract

- Task access remains administrator or original assignee/current owner/reviewer/release owner. A mention, follower, dependency, attachment, or shared URL does not grant task access.
- Administrator-only task creation, detail/assignment edits, project creation and configuration remain unchanged. Historical clients retain their original workflow contracts; the current UI uses the live discipline status contract below, including free movement out of completion. Workflow changes continue to use server-provided `allowedStatuses`.
- Return 401 for invalid sessions, 404 for inaccessible resources, 403 for forbidden operations on accessible resources, 400 for invalid input, and 409 for a stale version. Errors use `{ "message": "..." }`.
- Use GUID task/staff/account IDs and numeric comment IDs, UTC timestamps, optimistic versions, and transactional audit records. Notification inserts share the successful comment transaction; task access is rechecked when notifications are read.
- Resource-specific versions allow comment/checklist edits without unnecessarily conflicting with unrelated task detail edits. None of these proposals change the current task PUT contract until the server and client are coordinated.

## Discipline statuses — current UI/API

- Catalog table (2026-10-15): row Add/Edit/Delete reuse PUT /statuses, preserving stable codes, board mappings and hidden discipline lists. Saves apply per action; no second Save catalog step. Task use and assignment disable deletion with an explanation; To Do remains required. Usage comes from existing scoped administrator workspace tasks. Server transactionally rejects in-use deletion even if the client snapshot is stale. No additional endpoints or usage data are exposed.

- UI separation (2026-10-15): administrator /status-catalog edits definitions; /discipline-statuses edits membership/order. Both preserve hidden settings fields. Board presentation uses the dedicated catalog-aware contract below, with one editor, draft guard and Save board layout action.

- `GET /statuses` returns `{version,canManage,catalog:[{code,name,boardStatus,isCustom}],disciplines:[{discipline,statuses:[code]}]}`. Authenticated reads expose global status definitions only; no task counts, usage or task identifiers are exposed. `boardStatus` must be one canonical status already owned by a saved Board presentation column; it supplies initial/backward-compatible placement for codes without a saved explicit catalog board assignment. Administrator `PUT /statuses` takes the same editable catalog/disciplines plus expected `version`. Codes are stable (30 characters), names editable (80). To Do must retain its name and be first for both disciplines. Settings revisions are conflict tokens, not workflow versions.
- Save immediately changes the choices of existing/new tasks without rewriting task rows, ownership, pins, versions, activity or notifications. Every in-use task status must remain assigned to that task's discipline; removal returns 409. Catalog removal is possible only when unused/unassigned by the submitted definition. Parent settings locks serialize saves, live creates/detail edits and status moves. Settings changes preserve immutable before/after audit in the same transaction.
- `PUT /tasks/{id}/status` takes `{status,version,note?}` and returns scoped canonical task details. Only administrator or currently linked Original/Owner may move; Reviewer/Release visibility alone does not grant this permission. Any configured destination is permitted, including out of completion. No automatic handoff/review/release gate. SQL rechecks visibility, roles, membership and version; status/live flag/version, activity and owner notification commit atomically. No new access grant.
- `POST /tasks/live` creates an administrator task in To Do with no workflow pin. `PUT /tasks/{id}/live` saves details/notes without changing status or historical pin; only administrators edit fields/assignments, participants may add notes. Both reuse Staff Information IDs and existing SQL authorization/concurrency checks. Historical tasks may save ordinary details before their first status move. The stored live flag prevents incompatible clients from operating on the new state; `statusName` and `statusBoardStatus` are additive list/detail metadata.
- New UI uses `X-Live-Statuses: 1` alongside `X-Task-Workflow: 1` and the mutation header. Historical versioned workflow APIs below remain for compatibility, but the administration UI, task creation and current status moves do not use drafts/publishing/version selections. The old workflow administration URL redirects to `/discipline-statuses`. Existing tasks keep their current status and pin; live choices apply to all tasks. Board presentation retains its independent resource and saved four columns.
- Migration `045` seeds the four shared defaults once, preserves existing task data, drops the obsolete canonical-only check and adds a nonempty status constraint. Replaying `041` cannot restore the obsolete constraint, and replaying `045` cannot restore removed settings. Deploy the coordinated Server before the frontend; an older server rollback is unsupported after live status use.

## Historical discipline workflows — retained compatibility API

- Existing task rows retain a null `workflowVersionId`, the protected Legacy v1 behavior. Configuration never rewrites existing task status, ownership, version, history or notifications. Each new task uses the active workflow for its discipline, or Legacy v1 when none is active. Configured tasks pin an immutable published version; moving an existing task between workflows/disciplines is excluded.
- Definition: `{ mode, name, startStageId, stages: [{ id, name, kind, color, ownerRole }], transitions: [{ id, name, fromStageId, toStageId, actorRoles, kind, requireNote }] }`. Missing `mode` deserializes as `Advanced` for previously published definitions. New `Simple` definitions contain 2–10 unique named statuses, each with a stable lowercase slug ID. The first is the start and the last is the completion status. The server validates all generated pairwise moves and their `Original`/`Owner` actor roles; nonfinal stages retain the original Staff Information assignee, while completion clears the current owner. An original assignee may move back out of completion, and administrators retain their existing override. `In Review` is an ordinary name in Simple mode and has no approval/failure semantics. The previous `Advanced` format still validates its 2–30 stages and 1–100 actions, reviewer/release authority, required failure note and administrator-only cancel/reopen. Previously pinned Advanced tasks keep those rules.
- `GET /discipline-workflows` → `{ canManage, items: [{ discipline, active, draft }] }` for Development/Drafting. Published version: `{ id, discipline, versionNumber, definition }`; draft: `{ id, discipline, version, definition }`. Non-admin reads omit drafts. `POST /discipline-workflows/{discipline}/drafts` with `{}` copies the active definition or creates a default draft. `PUT /workflow-drafts/{id}` with `{ version, definition }` saves a draft. Both return the canonical draft.
- `POST /workflow-drafts/{id}/validate` with `{ version }` returns `{ errors: [string] }`; `POST /workflow-drafts/{id}/publish` with `{ version }` validates and publishes an immutable version, activates it for new tasks and removes the draft. `PUT /discipline-workflows/{discipline}/activation` with `{ workflowVersionId: null, expectedActiveVersionId }` disables new-task activation only. Configuration writes require Administrator, optimistic revision checks and atomic audit.
- Task list/details add `workflowVersionId` and embedded `workflow`; null means Legacy v1. For configured tasks, `status` is the stable stage ID and display names/purpose come from the pinned definition. Details retain server-provided `allowedStatuses` and add `allowedTransitions` with action IDs, destinations, note rules and resolved target owner. A role or required assignment change affects available actions without granting broader task visibility.
- `POST /tasks/{id}/transitions` with `{ transitionId, version, note }` returns canonical task details, or `{ taskId, accessLost: true }` when a successful handoff removes the acting user from task participants; the client acknowledges success and clears private task data. The server derives the next stage and owner and rechecks permissions, bindings, required notes and task revision transactionally; task changes, activity, audit and notifications commit together. Ordinary task PUT cannot change a configured task's stage, workflow pin or discipline. Administrator details edits still use existing task PUT, and stage handler rules constrain current-owner edits. New-task POST supplies the selected active `workflowVersionId`; an activation race requires explicit reload.
- Requests use `X-Task-Workflow: 1`. An unsupported client reading a configured task/list containing one, or creating under an active configured workflow, receives 426 with an upgrade message. Legacy endpoints retain their previous behavior. New clients fall back to explicit Legacy-only metadata only on a workflow endpoint 404; other failures block configuration/initial creation metadata rather than silently selecting Legacy.
- Frontend: protected admin status-list drafts, explicit conflict reload; independently guarded Redux metadata and task-action requests; configured task move form with note/navigation guards. Stage filters use `workflow-version-guid:stage-id` to distinguish identical names/IDs across versions. Calendar/dashboard completion calculations use stage purpose. Earlier feature data remains intact and dependencies/checklists do not gate transitions. Evidence: `simpleStatusWorkflow.js`, `disciplineWorkflows.js`, `DisciplineWorkflowsPage.jsx`, `taskWorkflow.js`, `taskTransitions.js`, `TaskWorkflowActions.jsx`, `TaskPage.jsx`, corresponding workflow tests, and sibling Server discipline-workflow models/controllers/services/procedures.

## Historical canonical board presentation — compatibility API

- `GET /workflow-presentation` → `{ version, canManage, groups: [{ id, name, color, statuses: [string] }] }`. All authenticated Task Management users read this application-wide metadata. It contains no task or participant data and grants no task access. Only administrators receive `canManage: true`.
- `PUT /workflow-presentation` with `{ version, groups }` replaces the complete presentation and returns its canonical trimmed definition with the next version (administrator only). Require 1–13 columns; unique IDs matching `[a-z0-9-]{1,40}`; plain-text names 1–80 characters; colors blue/amber/purple/green; all 13 canonical statuses exactly once. Arrays define ordering. Empty columns are allowed but omitted/duplicate/unknown statuses are not. Bodies are capped at 16 KiB. Missing/invalid input is 400, non-admin writes 403, stale versions 409.
- DB: additive `037_work_workflow_presentation`, `038_work_workflow_columns`, `039_work_workflow_column_statuses`, `040_work_workflow_presentation_history`. Seed the existing four groups only once. Reads and writes lock the singleton configuration before reading/replacing memberships; writes serialize and check the independent revision. Immutable before/after JSON, version, actor and time share the transaction; failures roll everything back. No task backfill, version increment, history rewrite or notification.
- UI: administrator `/board-presentation` editor supports add/remove-empty columns, names, theme colors, explicit column/status ordering and reassignment, default-layout draft, save and confirmed reload. Polling cannot replace dirty drafts; a newer definition requires explicit reload. Navigation/sign-out and pending requests are guarded. Board and dashboard grouping use the same Redux resource; task sorting and canonical status filters/URLs/CSV remain unchanged. Explicit drag targets still require `allowedStatuses`.
- Compatibility: endpoint 404 uses the existing four groups and disables configuration. Other failures remain errors, retaining last loaded presentation where safe. Late responses after logout/expiry cannot restore metadata; older reads cannot overwrite successful writes. Existing clients may show the original layout while retaining identical workflows. Deploy Server before frontend; rollback frontend leaves configuration stored and task data unchanged.
- Scope: this endpoint only configures Legacy v1 presentation and never changes its transition rules. Legacy API approval without a note remains accepted; the frontend still requests approval/failure notes. Development/Drafting stages and actions now use the separate discipline-workflow contract above. Project-specific workflows, new disciplines, arbitrary roles, checklist/dependency gates and migration of existing tasks remain excluded.

## 1. Threaded comments and mentions — implemented

- `GET /tasks/{id}/comments?after=0&limit=50` → `{ items, nextCursor: number|null, mentionablePeople }`. `after` is the last numeric comment ID; limit is 1–50; items are ordered by ID ascending, including deletion tombstones.
- `GET /tasks/{id}/comments/{commentId}` → a single comment, for conflict reload.
- `POST /tasks/{id}/comments` with `{ body, parentId: number|null, mentions: [{ staffId: guid, start: number, length: number }] }` → 201 comment and Location.
- `PUT /tasks/{id}/comments/{commentId}` with `{ body, parentId, mentions, version }` → updated comment; stale versions return 409. Parent cannot change.
- `DELETE /tasks/{id}/comments/{commentId}` with JSON `{ version }` → 204. Soft deletion empties the public body/mentions and preserves replies/history.
- Comment resource: `{ id, parentId, authorId, authorName, body, mentions: [{ staffId, name, email, start, length }], version, deleted, canEdit, canDelete, createdAtUtc, editedAtUtc }`. Author identity is the account; mention identity is staff. `mentionablePeople` provides the existing staff lookup fields, scoped to this task.
- Permissions: current task participants and administrators may comment; author or administrator may edit/delete only while retaining task access. Mention candidates must be Staff Information records linked to other active accounts with existing task access, including linked administrators. The signed-in account is excluded from candidates; self-mentions on create/edit return 400 with `You cannot mention yourself.` for all roles. Mentions never grant access. Newly added distinct recipients get one in-app notification; unchanged mention recipients on edit get none. Inbox permissions are rechecked on read.
- Bounds: plain text, nonblank body, 4,000 characters, at most 20 mention spans. Spans use UTF-16 offsets into exact `@Name` tokens, validated against current staff identity/access inside the transaction. Repeated mentions of one person may have separate spans. Replies target a top-level comment on the same task; retained deleted roots can continue receiving replies.
- DB: `024_work_task_comments.sql`, `025_work_task_comment_mentions.sql`, `026_work_task_comment_history.sql`, `v_WorkTaskMentionPeople`, `sp_WorkTaskCommentsGet/Save`. Task/author/parent/staff/recipient FKs, numeric identity, own version, snapshots, soft deletion and previous-version audit. Comment writes do not change task version/status or replace workflow/review notes. Comment/history/mention notification writes commit together.
- Evidence: sibling Server `Controllers/WorkTaskCommentsController.cs`, `Data/WorkTaskCommentRepository.cs`, `Tests/TaskManagementChecks/DiscussionChecks.cs`; frontend `TaskDiscussion.jsx`, `discussionState.js`, `commentMentions.js`, `tests/comments.test.js`. Discussion does not add email, rich text or comment-bound attachment endpoints.

## 2. File attachments — implemented; external links — proposed

- `GET /tasks/{id}/attachments` → plain array of `{ id, taskId, fileName, contentType, sizeBytes, sha256, uploadedById, uploadedByName, createdAtUtc, version, canDelete }`. Storage location/state are not exposed.
- `POST /tasks/{id}/attachments` multipart `file` + GUID `uploadId` → 201 metadata and Location. Reuse the upload ID on retry for the same file/task/uploader; completed retries are idempotent and failed attempts use new private keys.
- `GET /tasks/{id}/attachments/{attachmentId}/content` → authorized binary download.
- Proposed only: `POST /tasks/{id}/external-links` with `{ name, url, description }` (the `/links` path is now reserved for parent/child tickets) → 201 link metadata. No external-link UI or endpoint exists.
- `DELETE /tasks/{id}/attachments/{attachmentId}` with `{ version }` → 204.
- Permissions: current task participants/administrators may add and download; uploader or administrator may remove only while retaining current task access. Attachment changes have independent versions and add task History without changing task version/workflow. Invalid input is 400, inaccessible resources 404, forbidden removal 403, conflicts 409, storage failures 503.
- Bounds/storage: non-empty PDF/PNG/JPEG and Word (`.doc`, `.docx`), Excel (`.xls`, `.xlsx`), PowerPoint (`.ppt`, `.pptx`) up to 10 MiB, 12 MiB multipart request cap, validated signatures/extensions/types and sanitized filenames. Modern Office packages additionally require matching content-type metadata and a main document part; legacy formats use the shared compound-file header. Validation is not antivirus scanning or full document decoding. Private Local storage in Development, private S3 otherwise; downloads pass through the API. Soft removal retains bytes/audit indefinitely; failed and abandoned upload attempts have durable background cleanup.
- DB/evidence: `027_work_task_attachments.sql`, `028_work_task_attachment_cleanup.sql`, `sp_WorkTaskAttachmentsGet/Save/Fail/Cleanup.sql`, sibling Server controller/repository/storage services and `AttachmentChecks.cs`; frontend `TaskAttachments.jsx`, `attachmentState.js`, `attachmentValidation.js`, `tests/attachments.test.js`. Real S3/IAM and production deployment remain unverified. For future links, validate HTTPS URLs without fetching arbitrary destinations and store URL/name separately.

## 3. Checklists — implemented; child tickets — see Linked tickets

- `GET /tasks/{id}/checklist` → `{ items: [{ id, title, completed, order, version }], version, summary: { completed, total, version }, canManage, canComplete }`. Item IDs are numeric; the page version is the collection revision. Empty checklists start at revision 0 and are not seeded by reads.
- `POST /tasks/{id}/checklist` with `{ title, collectionVersion }` → 201 canonical checklist page and Location pointing to its GET. New items append and start incomplete.
- `PUT /tasks/{id}/checklist/{itemId}` with `{ completed?, title?, version }` → 200 canonical checklist page. The version is the item's own version. Participants may submit completion changes only; administrators may also rename.
- `PUT /tasks/{id}/checklist/order` with `{ itemIds: [number], collectionVersion }` → 200 canonical checklist page. Include every current active item exactly once; order follows the array. Administrator only.
- `DELETE /tasks/{id}/checklist/{itemId}` with `{ version }` → 204, administrator only. Deletion is soft and preserves private audit; reload the collection afterward. Already deleted/inaccessible items return 404.
- Bounds: one list per task, at most 200 active items, trimmed plain-text titles of 1–200 characters, 16 KiB request cap. No item assignments, named checklist groups, subtasks, completion workflow gates, or checklist notifications are included.
- Permissions: administrators manage structure; any current task participant may complete/reopen items. Existing task visibility and Staff Information bindings are rechecked inside write transactions. This includes Completed/Cancelled tasks without changing their status. Checklist membership never grants access. Standard 400/401/403/404/409 errors apply.
- Concurrency: every successful mutation advances the collection revision; edits/deletions and changed order positions advance affected item versions. Concurrent structural changes invalidate an old full-order request. Checklist mutations leave the task version, workflow, owners and notifications unchanged. Data, private snapshots and public task activity commit atomically.
- Existing list/detail task records add `checklistSummary: { completed, total, version }`; counts exclude deleted items and require no per-card requests. Task PUT input is unchanged. The client uses collection revisions independently from task versions, guards stale reads/mutations, clears caches on session/access/binding changes, and retains task/comment drafts during checklist saves.
- DB/evidence: Server tables `029_work_task_checklist_state.sql`, `030_work_task_checklist_items.sql`, `031_work_task_checklist_history.sql`, `sp_WorkTaskChecklistGet/Save`, additive `sp_WorkTasksGet` projection, `WorkTaskChecklistController`, `WorkTaskChecklistRepository`, `ChecklistChecks.cs`; frontend `TaskChecklist.jsx`, `checklistState.js`, `checklistEditor.js`, checklist tests. Reordering uses accessible Move up/Move down controls.
- Child tickets are separate tasks with independent visibility, status and owners, using the Linked tickets contract above. There are no `/subtasks` endpoints.

## 4. Following — implemented

- `PUT /tasks/{id}/follow` follows; `DELETE /tasks/{id}/follow` unfollows. Both return `{ isFollowed: boolean }`, are idempotent and derive the account from the Task Management session. No body or task version is required.
- Existing task list/detail records add actor-specific `isFollowed`. Only project task workspaces use `?following=1` to filter the already permission-scoped task list while preserving project-specific presentation. Client/project directory pages and the global task list do not apply the filter. No separate Following page or list endpoint is needed.
- Only users with existing task access may follow. Following never grants visibility, changes task version/ownership or saves task edits. There is no follower roster or administrator subscription-on-behalf API in this implementation.
- Table `058_work_task_followers` has unique `(task_id, user_id)` rows and no foreign keys. SQL validates associations and serializes changes on the task lock; explicit Task Management reset clears subscriptions. Access loss/inactive accounts suppress delivery and visibility; subscriptions can resume when access is restored.
- Status, Assigned To, due-date and new-comment changes deliver in-app notifications in the originating transaction. Exclude the actor and deduplicate against direct assignment/mention recipients for that operation. Comment edits and unrelated task detail changes do not generate follower alerts. Notification read state is independent of following. No email/desktop delivery is added.
- Evidence: Server `WorkTaskFollowingController`, `WorkTaskFollowingRepository`, `sp_WorkTaskFollowingSave`, `sp_WorkTaskFollowersNotify`, `TaskFollowingChecks`; frontend `taskFollowing.js`, `TaskFollowButton.jsx` and the project task following filter.

## 5. Labels — implemented; configurable disciplines — proposed

- `GET /labels` → `{ items: [{ id, name, color, active, version }] }`.
- `POST /labels` with `{ name, color }` → 201 label; `PUT /labels/{id}` with `{ name, color, active, version }` → label (administrator).
- Names are trimmed, 1–80 characters, case-insensitive unique including inactive definitions. Colors must be `#RRGGBB`. Definition versions start at 1; updates require `active` and the last-read `version`. Used definitions are deactivated rather than deleted. GET returns all definitions for administrators, only definitions attached to currently visible tasks for ordinary users, including inactive references. Lookups add the same scoped `labels` array.
- `PUT /tasks/{id}/labels` with `{ labelIds: [guid], version }` → `{ labels, version, updatedAtUtc }` (administrator). Supply the complete desired set of up to 20 distinct IDs, using the task version. Empty clears assignments; missing/null lists are rejected. Only active definitions may be newly assigned; existing inactive labels may be retained or removed. Successful saves advance task version/time and append task activity; workflow/owners and notifications are unchanged. Existing task PUT calls preserve label associations.
- Task list/detail records add `labels: [{ id, name, color, active, version }]`; definitions are read live rather than copied permanently onto task rows. No task read endpoint or response envelope changes.
- DB: idempotent tables `032_work_labels`, `033_work_task_labels`, `034_work_task_label_history`, with unique name/association indexes and FK references. Definition and assignment changes write immutable before/after snapshots in the same transaction. Task writes lock current visibility, task version and label eligibility. Failed writes roll back associations, task version, audit and activity. No hard-delete/history endpoint.
- Frontend: administrator Labels page, separately saved task label selection, board/dashboard/list/detail badges, and URL `label=id,id` filtering requiring every selected label. Names always render as text; hex colors use contrasting black/white text. Drafts participate in navigation/sign-out protection. Save a new task before assigning labels.
- Evidence: Server `WorkLabelsController`, `WorkLabelRepository`, `sp_WorkLabelsGet/Save`, `sp_WorkTaskLabelsSave`, `LabelChecks.cs`; frontend `labelState.js`, `LabelsPage.jsx`, `TaskLabels.jsx`, `LabelBadges.jsx`, `taskQuery.js`, `tests/labels.test.js`, `tests/label-render.test.js`.

Configurable disciplines remain a separate proposal, excluded from Phase B:
- `GET /disciplines` → `{ items: [{ id, name, active, version }] }`.
- `POST /disciplines` with `{ name }` → 201; `PUT /disciplines/{id}` with `{ name, active, version }` → discipline (administrator).
- Permissions: administrators configure and apply disciplines; ordinary users may read metadata used by their accessible tasks. Deactivate used definitions instead of removing references.
- DB proposal: discipline definitions with stable IDs. Migrate Development/Drafting without losing existing task values, change server enum validation deliberately, and expose compatible display names during migration. Phase B preserves the existing shared frontend discipline constant and server validation.

## 6. Deadline calendar — implemented; additional planning fields and Timesheet links — proposed

Phase E reuses existing `GET /tasks` and `GET /lookups`. `WorkTaskRecord.dueDate` comes from SQL Server's date column; the client reads its `YYYY-MM-DD` portion without timezone conversion. Existing `projectId`/`projectName` and `assigneeId`/`assigneeName` support project and current-owner filtering. The server already limits task results through the current Staff Information participant view; client filters never broaden that visibility. No new endpoint, payload, permission, migration or mutation was needed.

The Tasks Calendar view uses URL `view=calendar&month=YYYY-MM&assignee=<staff-guid|unassigned>` with the existing filter keys. Calendar dates include closed tasks; planning excludes Completed/Cancelled and divides matching tasks into overdue, today, tomorrow through today plus 30 days (inclusive), and no deadline. Today is browser-local and refreshes on minute/focus/visibility events. Calendar navigation does not change the planning horizon. Owner choices derive from visible tasks; project options also retain historical references present in visible tasks. Cards open existing versioned task editing, preserving the query. Existing Redux refresh/access/session cleanup is reused without a new private cache. Evidence: `calendar.js`, `TaskCalendar.jsx`, `TasksPage.jsx`, `taskQuery.js`, `tests/calendar*.test.js`; Server `WorkTaskRecord`, `sp_WorkTasksGet.sql`, `app.v_WorkTaskParticipants` in `Database/Tables/021_work_tasks.sql`.

The following extensions remain proposed and are not prerequisites for the deadline calendar:

- Extend task list/detail with `{ startDate: "YYYY-MM-DD"|null, estimateMinutes: number|null }` and existing PUT input with those fields plus version.
- `GET /tasks/{id}/timesheet-links` → `{ items: [{ entryId, userId, date, durationMinutes }], totalMinutes }` for entries the caller may see.
- `POST /tasks/{id}/timesheet-links` with `{ entryId: guid }` → 201 association; `DELETE /tasks/{id}/timesheet-links/{entryId}` → 204.
- Permissions: only administrators edit start/estimate. Linking requires access to both task and existing Timesheet entry; ordinary users can link/unlink their own entries, administrators only entries they are independently authorized to manage. Task login does not imply Timesheet login or broader Timesheet data access.
- DB: date start column, nonnegative integer estimate with defined upper limit, task-entry association with uniqueness and FKs to confirmed Timesheet schema. Enforce valid date ordering and preserve existing time records. Resolve actual Timesheet entry identity/authorization in the server before exposing the integration.

## 7. Dependencies (blocked by) — implemented, informational only

- `GET /tasks/{id}/dependencies` → `{ version, canManage, blockedBy: [{ taskId, code, title, status }], blocks: [...], changedTasks: [] }`. The version is the parent task version. Each neighbor must be visible to the caller; hidden IDs, titles, placeholders and counts are omitted. GET does not grant access or seed data.
- `POST /tasks/{id}/dependencies` with `{ blockedByTaskId, version }` → 201 canonical source page plus `changedTasks: [{ id, version, updatedAtUtc }]` for both endpoints; collection Location included. The source depends on the selected target. Administrator required, both task permissions checked transactionally.
- `DELETE /tasks/{id}/dependencies/{blockingTaskId}` with `{ version }` → 200 canonical source page and both changed task revisions. It removes only the directed relationship; task rows and audit remain. Missing relationship is 404, stale source version 409, duplicate/self/cyclic addition 400, inaccessible endpoint 404, forbidden mutation between visible tasks 403.
- Dependencies remain informational across projects and all statuses, including Completed/Cancelled. No automatic status transition restrictions, owner changes or notifications. Existing `allowedStatuses` and task PUT behavior are unchanged. Successful mutations advance both endpoint task versions/timestamps and append generic activity without neighboring identities or titles; this refreshes the inverse view and makes outstanding task edits conflict normally.
- DB: incremental `035_work_task_dependencies` unique directed pair/FKs/self-link check and reverse index; `036_work_task_dependency_history` immutable Add/Remove events with actor, time and both task versions. A transaction-owned SQL application lock serializes graph writes, so disjoint concurrent additions cannot jointly form a cycle. Iterative visited-set traversal handles deep/converging paths. Shared graph locks keep reads consistent; SQL failures roll back edges, both revisions, audit and activity. All mutations use the same lock order (graph before task rows).
- UI: saved task Details has Blocked by/Blocks links preserving task-list query state, administrator add/remove blocker controls and a removal dialog. Manage an inverse relationship on its dependent task. New tasks must be saved first. Selections participate in navigation/sign-out protection; task/label/dependency writes coordinate shared task versions. Own successful saves merge only version/time into existing task drafts. An independently newer task requires an explicit reload. Redux invalidates affected inverse pages and discards cached data/pending responses upon observed task-access loss or staff rebinding.
- Evidence: Server `WorkTaskDependenciesController`, `WorkTaskDependencyRepository`, `sp_WorkTaskDependenciesGet/Save`, `DependencyChecks.cs`; frontend `TaskDependencies.jsx`, `dependencyState.js`, `TaskPage.jsx`, `tests/dependencies.test.js`, `tests/dependency-render.test.js`. Workflow gates require a separate approved policy and remain excluded.

## 8. Email/digests and due reminders

- `GET /notification-preferences` → `{ emailEnabled, digestFrequency: "off"|"daily"|"weekly", timeZone, dueSoonDays, overdueEnabled, version }`.
- `PUT /notification-preferences` with the same fields/version → saved preferences for the caller.
- `GET /admin/notification-delivery` → delivery configuration/status (administrator, no secrets); `PUT /admin/notification-delivery` with validated sender/schedule/provider settings → configuration status (administrator).
- Reminder events reuse existing inbox records and may be delivered by email when the recipient opts in. Notification responses add `{ type, eventId }` so clients can distinguish assignment, review, mention, due-soon and overdue events.
- Permissions: own preferences only; server uses verified account email and current task access. No email is sent for historical notifications without an explicit delivery policy. Users can opt out, and administrator setup does not grant task visibility.
- DB: user preference/version rows, transactional event outbox, delivery attempts, retry/dead-letter status, deduplication `(recipient, task, reminder_type, local_date)` and digest grouping. Schedule in configured IANA time zones; suppress closed/cancelled work and inactive recipients. Provider configuration and secrets belong to server deployment settings.

## 9. Server pagination, search and sorting

- Proposed opt-in `GET /tasks?pageSize=50&cursor=&q=&discipline=&status=&projectId=&quickView=&sort=updatedAtUtc&direction=desc` → `{ items: [task], nextCursor, totalCount, summary: { total, inProgress, inReview, completed } }`.
- Notification pagination and All/Unread filtering are implemented by the current contract above. Free-text notification search and configurable sorting remain unimplemented.
- Keep existing unpaged responses compatible until callers migrate; alternatively introduce a separately versioned contract. Do not silently replace the existing task array with an envelope.
- Permissions: apply actor visibility before search, counts, sort and pagination; quick views derive the actor from the cookie, not a submitted user ID. Creator view requires `createdById`. Searches include descriptions and authorized participant display names. Whitelist sort keys/directions; parameterize values.
- DB: stable cursor ordering with unique ID tie-breaker, indexes for assignee/reviewer/release owner/creator, dates and status. Consider full-text indexing only after measuring search volume. Define page-size cap, cursor validation and time-zone semantics for overdue. Dashboard aggregate counts must not depend on the current page.

## 10. Live updates

- `GET /events` → cookie-authenticated SSE (`text/event-stream`) with heartbeat and events `{ eventId, type: "task.changed"|"notification.changed"|"access.changed", taskId?: guid, version?: number }`. Alternatively a dedicated SignalR hub at `/events/hub`; choose one transport during backend implementation.
- Support reconnection via `Last-Event-ID` and a reset event if replay retention is exceeded. Events signal clients to refresh authorized data; they must not carry task descriptions/account data to unauthorized subscribers.
- Permissions: dedicated Task Management authentication only. Re-evaluate current membership for events and immediately signal removal without exposing inaccessible task content. End streams on session invalidation/deactivation; do not put access tokens in URL queries.
- DB: transactional event outbox or durable change log, bounded replay cursor retention and multi-instance fan-out. Publish after commit, including notification read changes. Define reverse-proxy buffering/timeouts and heartbeat limits. Keep focus/manual refresh and a polling fallback for disconnected clients until live delivery is verified.
